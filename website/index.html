EmbeddedAn alternative to MongoDB on one machine

One document database for the browser, Node.js and Bun.

defuss-db stores documents in a browser worker, a Node.js process or a Bun process, with the same API in each. A transaction commits several collections together, a reader sees one snapshot, and a commit to a directory returns after it is flushed. The database runs inside your application, on one machine, with no server to operate.

Storage: OPFS in the browser, a data directory on the server, memory in both · TypeScript, ESM and CommonJS · MIT license

An embedded database for web apps

Choose defuss-db when your documents belong to one machine: a user's browser, a desktop or edge device, or a single server. The database is a library, so a read by ID costs no network round trip and there is no database server to deploy, secure or upgrade. When your rows already sit in a JavaScript array and need neither persistence nor indexes, query the array with DataView instead.

The same API in the browser and on the server

Collections, queries, indexes, transactions and history work the same in a dedicated browser worker, in Node.js and in Bun. A database opened with openMemory() in a test has the API of one opened with openOPFS() in a browser or openDirectory(path) on a server.

With persistence

openOPFS() keeps collections in the browser's Origin Private File System, from a dedicated worker. openDirectory(path) keeps them in a directory under Node.js or Bun, and openMemory() in memory for tests and caches. On a directory a commit returns once its data is flushed, and a store reopens with every committed document, also after its process was killed.

Transactions across collections

One transaction changes several collections and their index entries together. At commit the database checks what the transaction read. If another commit changed a document it read, or if any commit landed after it scanned, the commit fails with CONFLICT and writes nothing.

Try a pinned snapshot and a rollback

Indexes that seek, page and count

A compound index on tenant and score seeks straight to one tenant, returns its highest scores first and resumes from a cursor. A unique index rejects a duplicate key, also when two concurrent transactions claim the same key. An ID page or a range count reads index entries without decoding documents.

See index and scan timings

Efficient compaction

Index pages store keys with shared prefixes and numbers as varints, about a tenth of the bytes of plain object pages. Commits log their key changes and write index pages only at checkpoints: loading 100,000 documents with one ordered index wrote 29 MiB instead of 107 MiB. Once the connection is idle, a background copy drops old versions and puts documents back in key order, without blocking writers.

Read how compaction runs

Search by words or meaning

Full-text search ranks matching terms with BM25. Vector search finds documents with similar supplied embeddings. Hybrid search combines both rankings. A filter decides which documents qualify before the top hits are chosen.

Read a past price

Enable history on a collection. Read the price that applied on a date, correct one interval, reproduce what a reader saw before the correction, or restore a deleted document. Opt-in: _createdAt and _updatedAt on every write.

Native values between runtimes

Dates, maps, sets, bigints, typed arrays and cyclic references keep their JavaScript types in storage and in archives, so every runtime reads back the value that was written.

Backup and restore

db.export() writes one snapshot as a Brotli archive, compressed by defuss-brotli's WebAssembly build, with or without document history; exportStream() yields it in blocks for a file or an upload. db.import(archive) restores it atomically and rebuilds every index, into an empty database or merged with a conflict policy. An archive from a browser imports on a server, and the other way round.

defuss-db or MongoDB?

Both store schemaless documents with secondary indexes. MongoDB is a server that applications reach over the network; defuss-db is a library inside the application that uses it. Choose by where the data lives and how many machines must write it.

Choose defuss-db when

  • the data must live in the browser or keep working offline;
  • you want one data layer for browser and server code;
  • you need transactions across collections without running a replica set;
  • history, ranked search or native JavaScript values belong in the same store.

Choose MongoDB when

  • several machines or services must write the same data;
  • you need replication and failover;
  • query and write throughput matter more than running inside the application;
  • your code needs the MongoDB wire protocol, or operators and stages that defuss-db/mongo refuses, such as $lookup or $expr.

Built to scale without the bloat

defuss-db grows on the machine it runs on. It does not replicate, shard or federate, so there is no cluster to run and no network partition to handle.

defuss-db scales up

  • Reads by ID and index pages cost about the same at 10,000 and 100,000 documents.
  • Full-scan aggregates split across worker threads.
  • Concurrent writers share one flush per commit group.
  • Several processes can write one directory without losing an update.
  • A backup is one Brotli archive.

MongoDB scales out

  • Replica sets copy every write to other machines.
  • Sharding spreads a collection across servers.
  • Every query crosses the network to a server process.
  • The cluster is yours to run, upgrade and monitor.

Six parts of a read

The planner carries a query from a public descriptor to typed results. Each layer owns a different piece of the work.

Typed keys

The ID token keeps the type. The string "1", the number 1 and the bigint 1n can identify three documents.

Ordered tuples

Tuple components follow the declared sort directions. A typed ID breaks ties between equal tuples.

Candidate selection

A primary key, equality tuple or ordered range can narrow the input that DataView evaluates.

Pinned readers

The schema, index pointers and visible documents come from one read revision.

Query results

A bounded cache retains qualifying results. The collection's commit revision validates a hit after another collection changes.

Search generations

A changed search input updates its stored generation. A reader can reconstruct the engine for its own revision.

Follow one seek

An ID page with a continuation reads a bounded interval of a declared ordered index. It checks the collection version and returns typed IDs.

Index and storage trade-offs

The choice of read API determines which bytes the database needs and how it detects a concurrent change.

When should I add an ordered index?

Use it for repetitive range scans or sorted pages. Every indexed document adds a pointer and a corresponding write when the tuple changes.

What does an exact index count read?

It scans entries in the interval. It skips document lookup and decoding. Set maxScannedEntries to reject a range that exceeds your budget.

Can an ID cursor resume a document page?

Yes. Supply the same collection, index and interval. A write to that collection makes a live cursor stale. A pinned snapshot can continue.

What do range bounds compare?

They compare sort-key buckets. A null prefix includes missing and undefined values. Ordinary DataView predicates apply their own equality rules.

When does a query hit the cache?

The default policy admits repeated queries that process enough input and return a small result. Streams and transaction reads bypass the result cache.

What does a search index store?

The database persists text and vector inputs. The first query after opening or eviction builds the in-memory engine for that generation.

How do I back up or move a database?

Export a Brotli archive from a snapshot and import it into an empty database, in the same or another runtime. The operations guide covers history activation and full-history restores.

Validation scope and limits

Safety guarantees

These contracts hold for operations that complete successfully on the supported storage backends.

Atomic commit

A commit publishes every staged document and index change at once. A failed or aborted transaction publishes none of them.

Conflict detection

A commit fails with CONFLICT when a concurrent commit changed what the transaction read. The database never reruns your callback, so its side effects happen once; retry where that is safe.

Snapshot consistency

A query reads the schema, index entries and documents of one revision. An explicit snapshot keeps its revision until you close it.

Flushed commits

On directory storage a commit returns after one flush of its data, which ends in a checksummed commit record. After a killed process, the store reopens at the last commit whose record is intact. OPFS flushes its files but offers no directory sync.

Exact bounded count

A successful index count covers its whole interval. A count that would exceed its scan budget is rejected instead of truncated.

Typed IDs

The string "1", the number 1 and the bigint 1n identify three different documents. Positive and negative numeric zero are one ID.

Not covered: replication, failover, sharding, network file systems and any test that commits survive a power cut. On macOS, every flush asks the drive to empty its write cache, under Node.js and Bun. Validation scope and limits
